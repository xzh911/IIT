## 1. 状态栏白色问题（真机，最高优先级）

**现象**：位置对齐了，但状态栏区域是**白色**；官方是蓝色（首页蓝色头部延伸到状态栏）。用户疑问："是不是层级拆错了？背景图应该顶到状态栏里，而按钮/搜索框/扫码图标应该紧贴状态栏。"

**历史对照（两版 IPA 表现）**：
- 旧版（build #5，03:33）：状态栏蓝色 ✅ 但按钮/搜索/扫码**顶进状态栏点不到** ❌ → 壳是 edge-to-edge 全屏，但前端 CSS `safe-area-inset-top` 避让**没生效**。
- 新版（r5，今天）：位置对齐 ✅（PHASE1 §3-A3 的 MainViewController 下移 safeArea 生效）但状态栏变白 ❌ → 原生下移后 WKWebView 从安全区下方开始，页面蓝色头部不再延伸到状态栏，露出壳的背景白色。

**根因判断（证据充分，未验证代码）**：
1. 官方真实做法（HANDOVER §4.5 已定版）：**edge-to-edge 沉浸式** `StatusBarOverlaysWebView=true` + 前端 CSS 754 处 `safe-area-inset-top`/888 处 `safe-area-inset-bottom` + JS `StatusBar.styleLightContent()`（白色文字）。**不要学仿照版"下推白条"**。
2. 前端 `env(safe-area-inset-top)` 要生效**必须 `viewport-fit=cover`**（仿照版同款坑：`altweb.status_bar_fix_three_layer` 记忆）。官方 index.html 若缺该属性 → CSS safe-area 全失效 → 旧版按钮顶进状态栏的根因。
3. 结论：正确方案 = **壳恢复全屏（去掉原生下移）+ index.html viewport 加 `viewport-fit=cover` + 状态栏文字白色**。按钮/搜索框靠官方 CSS safe-area 自动避让，无需手工调整。

**待确认项（明天第一条）**：`web/www/index.html` 的 viewport meta 当前值；`ios/platforms/ios/.../MainViewController` 的 safeArea 改动现状；官方 index.html 原版 viewport（reference/cdn-www/index.html）。

## 2. 收入纳税明细页（`/IncomeTaxPayment/taxRecordList`）差异

**期望（官方形态）**：
1. 「请选择所得类型」筛选区：默认勾选 4 项（工资薪金/劳务报酬/稿酬/特许权使用费，左侧蓝色圆形勾选）；下面蓝色「其它类型」展开按钮 → 展开未勾选项（经营所得/利息、股息、红利/财产租赁/财产转让/偶然所得）+「收起」按钮。
2. 无勾选时下方「查询」按钮灰色不可点。
3. 查询结果：收入合计（带圆形问号提示）xx.xx 元 + 已申报税额合计 xx.xx 元（**按勾选的类型动态计算**，不是固定值）；下方按类型分组明细记录（工资薪金/劳务报酬…），记录可在 dev 面板改。

**根因判断（证据充分）**：
- 筛选项数据源 = `GET common/basecode/vn/SB_NEW_SRNSMXSDXM_YDWEB`（收入类型编码）。**当前 global-shared.json mock 为 `[]`**（session2 已实证消费 chunk 233 按 `{value,label}` forEach 渲染）→ 空数组 = 页面上没有任何筛选项 → 查询按钮/勾选/动态计算全灭。**这是最可疑的根因**。
- 列表/合计字段已有（`sreHj/ybtseHj/nsmxList`，API-UI-IMPACT §收入明细）→ 勾选筛选后动态合计 = 页面按所选类型过滤或请求体带类型参数（cxNsmxList 目前是静态 fixture 不区分请求体 → 需要 DYNAMIC 路由按请求体分支，方案已在 income-config/DYNAMIC 铺垫）。
- 分类明细记录可被 dev 面板改 = 现有覆盖层机制已支持（cxNsmxList 覆盖层，devpanel_v2_probe 已验证）。

**待确认项**：`SB_NEW_SRNSMXSDXM_YDWEB` 真实 8 项编码表（字段 {value,label}，value 大概率 = sdxmDm 如 0101/0401/…）；消费 chunk 233 里「默认勾选 4 项」「其它类型展开」「未勾选灰按钮」的判定逻辑；cxNsmxList 请求体是否带类型参数。

## 3. dev 面板问题（入口 + UX）

**反馈**：
1. 入口不应"随处点五下就能出来"→ 应**连点五下「我的」**这种特定位置才触发。
2. 面板"写得很不好用"→ 若不会设计，**参考仿照版（`reference/alternate-web/`，8082 试用版）的 dev 面板逻辑**。

**判断**：
- 入口改动：dev-entry.js 的 capture click 监听加命中判定（「我的」tab 元素 / 坐标区），5 连击窗口不变。**难度低（~0.5h）**。注意 WORK_REPORT §1.1 原始需求是「关于&更新→基本信息→自然人办税服务平台 5 连击」，用户现在改口要「我的」——以用户本次为准。
- UX 重设计：参照 alternate-web/site-8082 的界面（其 dev 面板结构：模板入口/表单/列表管理模式），在保持覆盖层契约（`{match,method,data}` + `etax_custom_overrides`）不变的前提下重写面板 UI（模板区→表单编辑已是 V2，用户嫌的是整体可用性：字段组织/保存反馈/导航）。**难度中（2-4h）**。

## 4. 纳税记录开具（完税证明页 `/taxProof/*`）差异

**反馈**：
1. 不应是"随机验证码栏"→ 官方是**滑块验证**：「请按住滑块，拖动到最右侧」，滑动过程左侧变绿，滑完出**绿色勾「验证通过！」**。
2. 「生成纳税记录」按钮一直灰蓝色不可点 → 应**始终可点击（蓝色）**。

**判断**：
- 当前"验证码栏"= `common/captcha/base64Image` miss → 走 AFS 兜底（规则 §captcha 保持 miss，PHASE1 §3-A4 曾拍板"照官方空转即可"）——但用户实测不满意，**这条规则要按用户反馈重开**。
- 官方滑块 = 需先确认组件来源：grep bundle 文案「请按住滑块/拖动到最右侧/验证通过」定位（大概率是安全键盘/极验 gt3/自绘滑块）。若组件在本地 bundle → 数据层 mock 让其通过即可（生成按钮依赖验证状态 → mock 校验接口返回成功）；若是极验（gt3，需联网）→ 本地模拟滑块组件替换或 mock gt3 插件回调。
- 生成按钮灰色 = 上游状态（验证未过 / kjcs 次数 / 某开关）没满足 → 顺滑块修复一起解。
- **难度：中（1-3h，取决于组件来源，需探一次确认）**。

## 5. 首页（`/zdj-home`）差异清单

**反馈**：
1. 顶部业务区不应该是静态「待处理事项 + 两条消息」→ 应是**橙色上下滚动换信息的模块**（左侧橙色小铃铛图标，滚动换信息）。
2. 待处理事项**设为 0**（不需要示例）。
3. 缺 **「2025 年综合所得汇算」box**：右上角「进入专题页」按钮；正文「已于6月30日结束，逾期办理可能会产生滞纳金，请您尽快申报」；右下角一部分图片；左下角蓝色「开始申报」按钮。
4. 首页下方缺：**左右滚动宣传栏**、**警示案例**、**通知公告**的具体文章条目。
5. 总体"长得不像"，通知栏白色很假（见 §1）。

**判断（均有官方组件/数据锚点，不是自绘）**：
- ① 橙铃铛滚动模块 = 待办事项卡的官方形态（queryTaskListV2 → `POST zrr/task/queryTodoTask`，chunk 40 `matterList`，query-task-v2.json 已 mock 2 条）。滚动换信息可能是该组件自带轮播/定时器逻辑（数据≥2 条即滚？）或需要特定字段。**难度低-中（0.5-1.5h，读 chunk 40 模板确认）**。
- ② 待办 0 条：query-task-v2.json 清空 content 即可。**低（0.1h）**。
- ③ 汇算专题 box：官方首页组件（年度汇算宣传卡），数据/开关待定位（搜 bundle「滞纳金/开始申报/进入专题页」文案找组件与数据源）；宣传页 = HAR 已捕获 `mobilezty/` 26KB HTML×多（session3 §1.3 有记录）但判定外部 H5 未本地化（`yata_v_0_1_11.js` 未在 HAR）→ 需从 wcdn 补下脚本或截图代替。**难度中（2-4h，含宣传页本地化）**。
- ④ 警示案例/通知公告 = `tzgg/lamp`、`tzgg/rdwt`、`tzgg/query` 无 fixture（PHASE1 §3-A2 已点名"首页黄条/警示案例/公告区块空"）→ 字段从 deob 提取（`tools/api-fields.js` + deob 树），半天。**难度中（半天）**。
